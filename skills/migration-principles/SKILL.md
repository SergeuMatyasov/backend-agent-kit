# Migration Principles

## Цель
Зафиксировать правила безопасной миграции, чтобы переносить код в новую архитектуру без
функциональных изменений, случайного изменения контрактов и преждевременного удаления legacy.

## Когда использовать
Используй этот skill, если нужно:
- переносить legacy-модуль, сценарий или сервис в clean architecture;
- отделять domain logic от application orchestration и infrastructure-кода;
- вводить порты, адаптеры, facade или anti-corruption layer;
- проводить пошаговую миграцию вместо полного переписывания;
- ревьюить PR с миграцией существующего поведения.

## Обязательные правила
1. Сохраняй поведение 1 в 1.
2. Не меняй названия, контракты, DTO, события, маршруты и форматы данных без явной необходимости.
3. Предпочитай adapter, facade или anti-corruption layer вместо прямого переписывания legacy-кода.
4. До изменения кода явно раздели, где находятся domain rules, application orchestration,
   infrastructure concerns и framework glue.
5. Сначала опиши текущее поведение, потом меняй реализацию.
6. Делай миграцию маленькими шагами с проверкой эквивалентности после каждого шага.
7. Каждый шаг должен завершаться явным списком:
   - что изменено;
   - что не изменено;
   - какие риски остались;
   - как проверить эквивалентность поведения.
8. Если эквивалентность нельзя подтвердить тестом, сравнением результатов или наблюдаемым
   контрактом, старую реализацию удалять нельзя.
9. Не смешивай миграцию поведения с новой функциональностью в одном шаге.

## Рекомендуемые практики
1. До старта фиксируй точку входа, входы, выходы и side effects.
2. Сначала добавляй characterization tests или другой способ сравнения до и после.
3. Переноси самый маленький сценарий, который можно изолированно проверить.
4. Оставляй старый API на месте и подключай новую реализацию через adapter или facade.
5. Явно отмечай места, где новая архитектура все еще зависит от legacy.

## Анти-паттерны
1. Big bang rewrite без промежуточной проверки поведения.
2. Одновременное изменение архитектуры, бизнес-правил и внешнего контракта.
3. Удаление legacy-кода до сравнения результатов до и после.
4. Перенос файла в новый слой без понимания его реальной ответственности.
5. Смешивание domain logic с transport, persistence или framework-specific кодом.

## Алгоритм принятия решений
1. Опиши текущий сценарий через точку входа, наблюдаемое поведение и side effects.
2. Раздели код на domain rules, application orchestration, infrastructure concerns и framework glue.
3. Выбери минимальный шаг миграции, который можно проверить отдельно.
4. Введи порт, adapter или facade без изменения внешнего поведения.
5. Сравни поведение до и после.
6. Только после подтверждения эквивалентности переходи к следующему шагу.

## Проверка перед завершением
1. Текущее поведение зафиксировано до начала изменений.
2. Внешние контракты не изменены без отдельного обоснования.
3. Границы между domain, application, infrastructure и framework glue названы явно.
4. Каждый шаг миграции можно проверить отдельно.
5. Legacy-код не удален до подтверждения эквивалентности поведения.
