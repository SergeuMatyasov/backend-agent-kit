# Stepwise Clean Architecture Migration

## Цель
Задать безопасный порядок шагов для поэтапной миграции legacy-кода в clean architecture без
big bang rewrite и без потери проверяемости поведения.

## Когда использовать
Используй этот skill, если нужно:
- переносить legacy-сценарий в Domain, Application и Infrastructure по шагам;
- вводить порты и адаптеры вокруг существующего API;
- уменьшать legacy-слой постепенно, а не одним переписыванием;
- планировать migration roadmap для одного модуля или use case.

## Обязательные правила
1. Выполняй шаги по порядку.
2. Не объединяй несколько соседних шагов в один большой перенос без отдельной проверки.
3. После каждого шага фиксируй:
   - что изменено;
   - что не изменено;
   - какие риски остались;
   - как проверить эквивалентность поведения.
4. Не удаляй legacy-код до шага сравнения поведения.
5. Если шаг нельзя проверить отдельно, сначала уменьши размер шага.

## Пошаговый алгоритм

### Шаг 1. Зафиксировать текущее поведение
Определи текущую точку входа, входы, выходы, side effects и наблюдаемый внешний контракт.
Добавь characterization tests, снимки ответов, сравнительные примеры или другой способ потом
сравнить поведение до и после.

### Шаг 2. Построить dependency map
Зафиксируй зависимости сценария: вызовы в БД, очереди, HTTP, framework-specific API, static helper,
наследование, shared DTO и другие точки сцепления.

### Шаг 3. Выделить domain model, use cases и interfaces
Отдели domain rules от orchestration. Назови use case, domain model и interfaces, которые нужны
сценарию, не меняя пока наблюдаемое поведение.

### Шаг 4. Ввести порты и адаптеры без изменения поведения
Добавь ports, adapters, facade или anti-corruption layer вокруг legacy-зависимостей. Старый API
должен продолжать работать через новую границу без изменения результата.

### Шаг 5. Перенести один маленький сценарий
Выбери минимальный изолируемый use case и перенеси только его. Не мигрируй весь модуль сразу,
если эквивалентность нельзя подтвердить быстро.

### Шаг 6. Подключить старый API через adapter или facade
Сохрани старую точку входа и направь ее на новую реализацию через adapter, facade или совместимый
слой перевода. Потребители не должны заметить смену внутренней реализации.

### Шаг 7. Сравнить поведение до и после
Проверь результаты, побочные эффекты, ошибки и контракты до и после миграции. Любое различие
считай дефектом миграции, пока не доказано обратное.

### Шаг 8. Удалить мертвый legacy-код только после проверки
Удаляй старую реализацию только после подтвержденной эквивалентности поведения и после того,
как новая цепочка вызовов стала единственным рабочим путем.

## Рекомендуемые практики
1. Начинай с самого узкого сценария, а не с самого заметного legacy-класса.
2. Явно помечай временные adapters и facade, чтобы потом их можно было убрать.
3. Храни dependency map и результаты сравнения рядом с задачей миграции.
4. Если сценарий затрагивает внешний контракт, выноси это в отдельный change set, а не в шаг миграции.

## Анти-паттерны
1. Сначала переписать все слои, а потом пытаться восстановить старое поведение.
2. Вводить новые use case и одновременно менять публичный API.
3. Переносить модуль целиком без промежуточных точек проверки.
4. Подключать новую реализацию напрямую, не оставляя совместимый adapter для старого API.
5. Удалять legacy-код сразу после компиляции новой реализации.

## Проверка перед завершением
1. Все восемь шагов либо выполнены, либо явно отмечено, почему следующий шаг еще не начат.
2. После каждого шага есть список измененного, неизмененного, рисков и способа проверки.
3. Старый API остается совместимым до подтверждения эквивалентности.
4. Удаление legacy-кода произошло только после сравнения поведения до и после.
