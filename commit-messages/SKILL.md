# Commit Messages

## Цель
Зафиксировать единый формат commit message для проекта, чтобы история изменений:
- была связана с задачами;
- быстро читалась в git log;
- показывала тип изменения без чтения diff;
- оставалась пригодной для поиска и ревью.

## Когда использовать
Используй этот skill, если нужно:
- написать commit message для нового коммита;
- подготовить message для squash или rebase;
- проверить качество commit history перед PR;
- предложить пользователю готовый commit title и body после этапа правок.

## Обязательные правила
1. Первая строка commit message должна иметь формат `<ticket> <type>(<scope>): <subject>`.
2. Номер задачи обязателен и всегда должен идти первым.
3. `type` должен быть одним из фиксированного набора: `feat`, `fix`, `refactor`, `chore`, `test`, `docs`.
4. `scope` обязателен, должен быть коротким, стабильным и отражать подсистему, модуль или техническую область.
5. `scope` должен быть в нижнем регистре и без расплывчатых слов вроде `stuff`, `misc`, `changes`, `code`.
6. `subject` должен быть коротким, в одной строке и описывать суть изменения без воды.
7. `subject` должен быть написан в инфинитиве: `добавить`, `исправить`, `обновить`, `вынести`, `удалить`.
8. В одном commit message не смешивать несколько независимых изменений. Один коммит должен описывать одно логически цельное изменение.
9. Если коммит нетривиальный, после пустой строки должен идти body в виде короткого списка ключевых изменений.
10. Если коммит затрагивает миграции, индексы, breaking changes или важные технические ограничения, это должно быть явно отражено в body.

## Разрешенные type
1. `feat` - новая функциональность.
2. `fix` - исправление бага или дефекта поведения.
3. `refactor` - изменение структуры кода без изменения поведения.
4. `chore` - технические изменения без бизнес-логики: конфиг, инфраструктура, зависимости, миграции.
5. `test` - добавление или изменение тестов.
6. `docs` - документация и описания.

## Правила для scope
1. Использовать короткие и повторно применимые scope.
2. Scope должен помогать искать историю по модулю, а не пересказывать весь diff.
3. Предпочтительны доменные или технические области: `contract`, `finstate-sync`, `repository`, `migrations`, `main-context`, `domain`.
4. Если изменение затрагивает вертикальный slice, использовать общий осмысленный scope для всего change set, а не перечислять все затронутые слои.

## Правила для subject
1. Subject должен отвечать на вопрос "что изменено", а не "как автор работал".
2. Предпочтительно формулировать subject через результат: `добавить ContractFinancialStateSync`, `исправить unique index по contract_id`.
3. Не использовать разговорные и размытые формулировки: `сделать`, `поправить кое-что`, `обновить изменения`.
4. Не дублировать в subject детали, которые лучше вынести в body.
5. Не растягивать subject перечислением всех слоев и файлов.

## Рекомендуемые практики
1. Для небольших коммитов оставлять только первую строку без body.
2. Для коммитов, затрагивающих несколько слоев, добавлять body списком из 3-7 пунктов.
3. В body писать только то, что полезно ревьюеру: ключевые изменения, ограничения, миграции, индексы, совместимость.
4. Сохранять единый языковой стиль: `ticket`, `type` и `scope` на английском, описание на русском.
5. Если большой change set можно разделить на независимые коммиты без потери смысла, лучше разделить.
6. Если изменение атомарное и вертикальное, допустим один коммит с хорошим body вместо искусственного дробления.

## Анти-паттерны
1. Коммит без номера задачи.
Плохо: `feat(finstate-sync): добавить ContractFinancialStateSync`
Лучше: `CLCT-570 feat(finstate-sync): добавить ContractFinancialStateSync`

2. Неразборчивый subject.
Плохо: `CLCT-570 fix(sync): fixes`
Лучше: `CLCT-570 fix(finstate-sync): исправить дублирование записей по contract_id`

3. Слишком общий scope.
Плохо: `CLCT-570 feat(stuff): добавить сущность`
Лучше: `CLCT-570 feat(finstate-sync): добавить ContractFinancialStateSync`

4. Слишком длинный заголовок с перечислением всего diff.
Плохо: `CLCT-570 feat(finstate-sync): сделать много изменений связанных с синхронизацией финсостояния договора и подключить сущность в контекст`
Лучше: `CLCT-570 feat(finstate-sync): добавить состояние синхронизации финсостояния договора`

5. Коммит с несколькими независимыми целями.
Плохо: один commit message одновременно про новую сущность, unrelated refactor и исправление тестовой инфраструктуры.
Лучше: разделить изменения на отдельные коммиты, если они не образуют один цельный сценарий.

## Примеры

### Do
```text
CLCT-570 feat(finstate-sync): добавить ContractFinancialStateSync

- добавить сущность и enum статусов в Domain
- подключить сущность в IMainContext и MainContext
- добавить repository и EFCore-реализацию
- добавить EF configuration с jsonb payload
- добавить unique index по contract_id
- создать migration для новой таблицы
```

```text
CLCT-612 fix(finstate-sync): исправить дублирование записей по contract_id
```

```text
CLCT-700 docs(contract): описать сценарий синхронизации финсостояния
```

### Don't
```text
Добавил новую сущность синхронизации финсостояния
feat(contract): update
CLCT-570 chore(code): changes
CLCT-570 fix(stuff): поправить всякое
```

## Алгоритм принятия решений
1. Определи номер задачи и поставь его первым.
2. Выбери `type` по сути изменения, а не по объему diff.
3. Выбери короткий `scope`, который стабильно описывает область изменений.
4. Сформулируй `subject` в инфинитиве и сократи его до одной ясной мысли.
5. Проверь, не скрывает ли текущий коммит несколько независимых изменений.
6. Если коммит нетривиальный, добавь body списком с ключевыми деталями для ревью.
7. Отдельно проверь, что миграции, индексы и breaking changes явно упомянуты.

## Проверка перед завершением
1. В начале message стоит номер задачи.
2. Заголовок соответствует шаблону `<ticket> <type>(<scope>): <subject>`.
3. `type` входит в разрешенный список.
4. `scope` короткий, понятный и не расплывчатый.
5. `subject` написан в инфинитиве и не перегружен деталями.
6. При необходимости добавлен body с ключевыми изменениями.
7. Commit message описывает одно логически цельное изменение.
