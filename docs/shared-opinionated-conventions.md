# Shared Opinionated Conventions

## Зачем нужен этот файл

`backend-agent-kit` по умолчанию старается оставаться reusable shared-слоем.

Но часть правил может быть не полностью нейтральной, а опираться на устойчивые инженерные соглашения,
которые сознательно стандартизированы во всех сервисах владельца этого kit.

Этот файл фиксирует, какие именно shared-артефакты допустимо делать opinionated,
чтобы это не выглядело как случайный drift shared-слоя в сторону одного репозитория.

## Когда opinionated shared-правило допустимо

Правило можно оставить в shared-слое, даже если оно не универсально для любого .NET-проекта,
если одновременно выполняются условия:

1. Соглашение реально используется во всех или почти всех сервисах, для которых ведется этот kit.
2. Это не локальная прихоть одного репозитория, а устойчивый cross-service engineering standard.
3. Правило улучшает безопасность, качество или предсказуемость кода сильнее, чем снижает универсальность.
4. Из правила можно явно понять его границы и случаи, когда нужен explicit exception.
5. Если сервис не использует это соглашение, его можно безопасно переопределить локальным repo-specific слоем.

## Когда правило нельзя тащить в shared

Правило должно оставаться repo-specific, если:

1. Оно завязано на один bounded context, локальный naming или конкретную бизнес-модель.
2. Оно зависит от инфраструктуры, которой нет в остальных сервисах.
3. Оно конфликтует с реальными паттернами нескольких сервисов сразу.
4. Оно требует знания конкретных путей, типов, extension methods или naming-артефактов только одного репозитория.
5. Оно не выдерживает перенос хотя бы в один соседний сервис без правок по сути.

## Текущие допустимые opinionated shared-конвенции

### DI registration через интерфейсы и reflection

В этом kit допустимо, что shared DI guidance исходит из следующего базового стандарта:

- сервисы регистрируются преимущественно через service interfaces;
- lifetime задается marker-interface паттерном;
- bulk registration и wiring часто строятся на reflection/scanning;
- special framework types и disposable adapters регистрируются явно, а не через blind scan.

Почему это допустимо в shared-слое:

- это общий стандарт семейства сервисов, а не локальная особенность одного репозитория;
- он влияет на безопасность DI graph и на типичные runtime-failures;
- его можно сформулировать как reusable engineering rule, а не как Leo.Products-specific деталь.

Что все еще нельзя тащить в shared даже здесь:

- конкретные имена marker interfaces только одного репозитория, если они не являются общим стандартом;
- локальные extension method names, если они не повторяются по всему набору сервисов;
- ссылки на один конкретный проект как на единственный допустимый layout.

## Как действовать, если новое правило спорно

1. Сначала проверь, это real cross-service convention или особенность одного сервиса.
2. Если правило reusable, но opinionated, зафиксируй его границы в shared docs и оставь в shared-слое.
3. Если правило локальное, вынеси его в `.github/*` consumer-репозитория.
4. Если сомнение остается, лучше считать правило repo-specific, пока не доказано обратное.
