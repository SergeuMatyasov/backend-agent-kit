# README Documentation

## Цель

Этот skill нужен для создания и обновления README-файлов, которые объясняют внутреннюю бизнес-логику, flow обработки и последовательность вызовов внутри системы.

Ожидаемый результат:
- человек открывает README и быстро понимает, откуда начинается процесс;
- видит, какие шаги выполняются дальше;
- понимает, где находятся развилки и почему система выбирает тот или иной путь;
- видит, какие данные читаются, что меняется в памяти, когда создаются события и в какой момент запускается следующая стадия обработки;
- может читать документ сверху вниз без необходимости сразу открывать код.

Этот skill задает формат документации по умолчанию для подобных README в этом репозитории.

---

## Когда использовать

Используй этот skill, если нужно:
- создать новый README с описанием внутреннего процесса;
- обновить README после изменения бизнес-логики;
- документировать flow сервиса, handler, event processor, preparation pipeline или orchestration-сценарий;
- объяснить путь от точки входа до финального действия системы;
- описать sequence из command, query, internal service, state mutation и final processing step;
- сделать документацию понятной человеку, который не хочет читать код построчно.

Не используй этот skill как основной, если задача про:
- публичный API contract;
- OpenAPI/Swagger описание;
- install/run инструкции проекта;
- описание CI/CD или инфраструктурного bootstrap;
- создание SKILL-файла, не связанного с README-документацией.

## Эталонный пример

Ориентир по стилю, плотности и уровню детализации:

- `src/DebtRecalcService.Infrastructure/InternalServices/EventProcessor/InterestAccrual/README.md`

Используй этот README как образец того, как нужно:
- вести читателя от верхней точки входа к финальному действию;
- объяснять бизнес-логику простыми словами;
- связывать секции с реальными классами и методами;
- показывать не только happy path, но и ветки skip, stop, save-only и process-further.

Нельзя слепо копировать доменные слова из эталона в другой README.
Нужно переносить структуру мышления, а не конкретные названия сущностей.

## Обязательные правила

### 1. Документация должна строиться по реальному flow кода

README должен описывать фактический путь выполнения, а не желаемую архитектуру и не абстрактную схему.

Обязательно:
- сначала найти реальную точку входа;
- понять, какие методы реально вызываются дальше;
- проверить ключевые ветки и условия;
- описывать только существующее поведение.

Запрещено:
- додумывать шаги, которых нет в коде;
- смешивать текущее поведение и планы на будущее;
- писать архитектурные общие слова вместо конкретного flow.

---

### 2. README должен быть линейным и легко читаемым сверху вниз

Формат по умолчанию для этого репозитория:
- обычный Markdown;
- последовательные заголовки;
- короткие абзацы;
- маркированные списки там, где перечисляются шаги, условия или результаты.

По умолчанию не использовать:
- HTML `details/summary`;
- раскрывающиеся деревья;
- искусственно сложную вложенность;
- формат, который мешает быстрому чтению.

Если пользователь отдельно просит другой формат, можно отступить от этого правила.
Во всех остальных случаях README должен быть обычным линейным документом.

---

### 3. В начале README нужно сразу объяснить, что именно делает процесс

Первые абзацы README должны без воды объяснять:
- какой процесс документируется;
- от какого вызова начинается путь;
- до какого результата документ доводит читателя;
- в чем общая идея процесса в 2-4 коротких пунктах или предложениях.

Хорошо:
- читатель сразу понимает цель документа;
- читатель сразу видит, где начинается flow;
- читатель понимает, что документ объясняет последовательность действий, а не общую теорию.

Плохо:
- длинное абстрактное вступление;
- пересказ предметной области без указания процесса;
- отсутствие явной точки входа.

---

### 4. Главную точку входа нужно называть явно

В начале README обязательно нужно назвать:
- файл;
- класс;
- метод или главный handler/service entrypoint.

Принцип:
- читатель должен сразу видеть, с какого метода начинается маршрут по документу;
- структура README должна идти в том же порядке, в каком логика идет в коде.

Предпочтительно указывать точку входа отдельной строкой или в первой основной секции.

---

### 5. Секции README должны повторять реальный порядок выполнения

Главный принцип структуры:
- одна секция = один крупный этап flow;
- внутри секции объясняется, что происходит на этом этапе и зачем он нужен;
- следующая секция идет только после предыдущей по реальному порядку вызовов.

Правильно:
- входная точка;
- режимы или ветки верхнего уровня;
- batch/scope/unit-of-work стадия;
- подготовка одной сущности;
- агрегирование результатов;
- финальное решение;
- короткая итоговая схема;
- карта файлов.

Неправильно:
- сначала рассказать про низкоуровневый helper;
- потом вернуться к верхнему service;
- потом снова уйти в query;
- тем самым ломая читаемый маршрут.

---

### 6. Каждый крупный шаг должен отвечать на пять вопросов

Для каждой важной секции README нужно явно или неявно ответить на вопросы:
- что запускается на этом шаге;
- зачем этот шаг существует;
- какие данные, state или сущности он использует;
- что он меняет, создает или решает;
- куда flow идет дальше.

Если после чтения секции нельзя понять хотя бы один из этих пунктов, секция недоописана.

---

### 7. Ветки и условия нужно выносить отдельно

Если логика разветвляется, ветки нельзя прятать внутри длинного абзаца.

Нужно явно описывать:
- условие входа в ветку;
- что именно делает система в этой ветке;
- почему это важно;
- какой следующий шаг после этой ветки.

Особенно важно явно документировать:
- skip branch;
- no-op branch;
- save-only branch;
- create-event branch;
- use-existing-entity branch;
- fail/stop branch;
- safety wrapper branch, если есть monitor, lock или другой защитный механизм.

---

### 8. Документация должна разделять подготовку, принятие решения и фактическую обработку

Если процесс сначала подготавливает данные, потом принимает решение, а потом при необходимости запускает следующий механизм, эти части нужно разделять явно.

Читатель должен видеть разницу между:
- подготовкой данных;
- read-only проверкой;
- изменением state;
- созданием pending event;
- запуском следующей стадии process chain;
- обычным сохранением без запуска дальнейшей обработки.

Если эти смыслы смешаны, README перестает объяснять логику и начинает путать этапы.

---

### 9. Если шаг работает только в памяти или не использует базу, это нужно писать явно

Для бизнес-flow документации это важно, потому что меняет смысл шага.

Нужно явно отмечать случаи, когда:
- шаг работает только с already loaded state;
- база на этом шаге не используется;
- изменение живет только в текущем scope;
- реальное persisted side effect произойдет позже;
- на шаге создается только pending entity, а не выполняется финальная операция.

---

### 10. Нужно объяснять не только что происходит, но и зачем это важно

После перечисления действий секции нужно, когда это действительно помогает, коротко объяснять смысл:
- почему этот шаг вынесен отдельно;
- зачем нужна эта ветка;
- от какой ошибки или дублирования она защищает;
- почему система в этом случае не идет дальше.

Но объяснение должно быть коротким и прикладным.
Не превращай README в теоретическую статью.

---

### 11. Язык документации должен быть простым и прикладным

Базовые правила языка:
- пояснения писать простыми русскими фразами;
- технические термины, имена методов, классов и enum оставлять в оригинале;
- не перегружать текст формальными оборотами;
- избегать канцелярита;
- избегать жаргона там, где можно сказать проще.

Нужно писать так, чтобы документ можно было читать без переключения в режим расшифровки сложных формулировок.

---

### 12. По умолчанию не использовать кодовые вставки

Если пользователь не просил примеры кода, README должен объяснять процесс словами, а не кодом.

Допустимо:
- упоминать имена методов и классов;
- ссылаться на файлы;
- называть команды, queries, services, events и поля.

Не нужно по умолчанию:
- вставлять code blocks;
- копировать куски методов;
- показывать сигнатуры ради сигнатур;
- превращать README в выдержку из исходников.

Цель документа:
- объяснить логику;
- не дублировать код.

---

### 13. В конце README должны быть краткая итоговая схема и карта файлов

Для таких документов обязательны две финальные секции:

1. Короткая логика принятия решения.
2. Карта файлов.

Первая нужна, чтобы читатель быстро повторил весь flow после подробного чтения.
Вторая нужна, чтобы читатель понял, где именно лежат ключевые части реализации.

Карта файлов должна содержать:
- только реально участвующие файлы;
- короткое описание роли каждого файла;
- минимально достаточный набор, без лишнего шума.

---

### 14. README должен быть самодостаточным

Хороший README позволяет понять основную механику без постоянных прыжков в код.

Это не значит, что нужно переписать все исходники.
Это значит, что после чтения документа читатель должен понимать:
- где начинается процесс;
- что происходит по шагам;
- где появляются решения и ветки;
- в какой момент есть side effect;
- когда запускается следующий этап обработки;
- когда система просто сохраняет подготовленные изменения.

---

## Рекомендуемая структура README

Ниже шаблон структуры, который нужно использовать по умолчанию для внутренней документации flow.

```md
# <Название процесса>

Короткое описание процесса и границ документа.

Идея процесса простая:
- ...
- ...

Главная точка входа: <файл / класс / метод>.

## 1. Верхняя точка входа: <Class.Method>

### 1.1. Первая верхнеуровневая ветка или режим

### 1.2. Вторая верхнеуровневая ветка или режим

## 2. Обработка одного batch / scope / unit of work

## 3. Работа внутри scope / context / pipeline

## 4. Подготовка одной сущности

### 4.1. Первый внутренний шаг

#### 4.1.1. Более локальный шаг

#### 4.1.2. Еще один локальный шаг

### 4.2. Применение решений к state

### 4.3. Поиск уже существующего результата

### 4.4. Ветка отказа / skip / no-op

### 4.5. Финальная проверка перед созданием нового события

### 4.6. Создание нового события или команды

### 4.7. Итог подготовки одной сущности

## 5. Как собирается общий результат

## 6. Финальное решение

### 6.1. Когда запускается следующий этап обработки

### 6.2. Когда происходит только сохранение

## 7. Короткая логика принятия решения

## 8. Карта файлов
```

Этот шаблон не нужно копировать механически.
Нужно адаптировать его под конкретный flow, сохраняя принцип:
- сверху вниз;
- от внешнего к внутреннему;
- от входа к финальному действию.

## Как должна выглядеть секция

Хорошая секция обычно состоит из четырех частей:

1. Заголовок с названием этапа.
2. Короткий вводный абзац на 1-3 предложения.
3. Список конкретных действий, условий или эффектов.
4. Короткое пояснение, почему этот шаг важен, если без него смысл неполный.

Пример удачного ритма секции:
- сначала назвать шаг;
- потом сказать, что именно делает система;
- потом перечислить действия;
- потом выделить бизнес-смысл или ограничение.

Если секция слишком длинная, ее нужно делить на под-секции, а не превращать в сплошной текст.

---

## Как писать заголовки

Рекомендуемый формат заголовков:
- `## 1. Верхняя точка входа: Class.Method`
- `### 1.1. Режим useMonitor = true`
- `## 4. Подготовка одного договора: SomeService.PrepareAsync`
- `#### 4.1.2. EvaluateSomethingQuery`

Правила:
- заголовок должен помогать навигации;
- в заголовке полезно указывать класс и метод, если это реально улучшает понимание;
- нумерация должна быть последовательной;
- заголовки не должны быть слишком общими.

Плохо:
- `## Логика`
- `## Что происходит дальше`
- `## Разное`

Хорошо:
- `## 3. Работа внутри scope: IScopeEventProcessorInterestAccrualService.ProcessScopeAsync`
- `### 4.2. ApplyRequestedActions`
- `### 6.1. pendingContractEventsApplier.ApplyPendingContractEventsAsync`

---

## Как писать про бизнес-логику

При описании шага нужно раскрывать не только техническое действие, но и его бизнес-смысл.

Хорошо:
- "Если дата начисления находится в будущем, новое событие не создается и pending events не запускаются. Подготовленные изменения просто сохраняются."

Плохо:
- "Потом вызывается query и что-то решается."

Хорошо:
- читатель понимает условие;
- понимает, что именно не происходит;
- понимает, какой путь выбирается дальше.

---

## Как писать про state и side effects

Если процесс меняет данные, создает события или, наоборот, только готовит state, это нужно называть прямо.

Всегда фиксируй:
- изменение происходит только в памяти или уже сохраняется;
- создается новый event или используется существующий;
- запускается ли реальная обработка или только подготовка;
- какой этап отвечает за final persistence или processing.

Именно эти места чаще всего критичны для понимания flow.

---

## Как писать краткую итоговую схему

Секция с короткой логикой принятия решения должна быть компактной.

Ее задача:
- в 8-15 пунктов повторить весь путь в сжатом виде;
- позволить быстро освежить flow без повторного чтения всех подробностей.

Хороший формат:
- пришел список сущностей;
- произошла фильтрация;
- данные загрузились в память;
- выполнилась подготовка;
- появились или не появились события;
- система либо запустила следующий этап, либо просто сохранила изменения.

Плохо:
- пересказывать всю документацию заново длинными абзацами.

---

## Как писать карту файлов

Карта файлов должна быть в самом конце документа.

Для каждого файла нужно указать:
- путь;
- краткую роль;
- почему этот файл важен в описанном flow.

Пример хорошей записи:
- `<path/to/File.cs>` — orchestration верхнего уровня: принимает входные данные, делит их на пачки, создает scope и передает управление дальше.

Карта файлов не должна:
- повторять вообще все файлы из папки;
- превращаться в каталог проекта;
- перечислять файлы без объяснения их роли.

## Анти-паттерны

### 1. Документация без явной точки входа

Плохо:
- читателю неясно, с какого метода начинается путь;
- секции не складываются в единый маршрут.

Как правильно:
- в начале README явно назвать основной service/handler/method.

---

### 2. Описание темы вместо описания flow

Плохо:
- документ рассуждает про начисление процентов в целом, но не показывает, как система реально идет по шагам.

Как правильно:
- описывать фактическую последовательность действий в коде.

---

### 3. Слишком абстрактные формулировки

Плохо:
- "сервис обрабатывает данные";
- "система делает нужные проверки";
- "потом что-то сохраняется".

Как правильно:
- называть конкретный шаг, конкретное решение и конкретный результат.

---

### 4. Скрытие логики в HTML-раскрывашках по умолчанию

Плохо:
- документ сложно читать сверху вниз;
- теряется обзор всего процесса;
- основные ветки приходится постоянно раскрывать вручную.

Как правильно:
- использовать обычные markdown-заголовки и плоскую навигацию.

---

### 5. Смешение подготовки и фактической обработки

Плохо:
- читателю непонятно, когда система только меняет state в памяти, а когда уже запускает настоящий processing chain.

Как правильно:
- отдельно описывать подготовку, применение решений, создание pending entities и финальный запуск следующего этапа.

---

### 6. Отсутствие важных веток

Плохо:
- описан только основной happy path;
- не описано, когда ничего не создается;
- не описано, когда система просто сохраняет изменения;
- не описано, когда используется уже существующее событие.

Как правильно:
- документировать все ветки, которые меняют итоговое поведение процесса.

---

### 7. README как пересказ кода

Плохо:
- документ повторяет имена методов без объяснения смысла;
- текст превращается в список вызовов без бизнес-логики.

Как правильно:
- связывать технические шаги с их смыслом и результатом.

---

## Примеры

### Хорошо: вступление

```md
# Подготовка данных для X

Этот документ описывает путь от вызова сервиса X до момента, когда система либо запускает Y, либо просто сохраняет подготовленные изменения.

Идея процесса простая:
- сначала система подготавливает данные;
- потом проверяет условия;
- затем либо запускает следующий этап, либо завершает flow без него.

Главная точка входа: SomeEntryService.cs.
```

Почему хорошо:
- сразу понятна граница документа;
- сразу названа цель;
- сразу обозначен entrypoint.

### Плохо: вступление

```md
# README

В этом файле описана логика системы. Ниже приведены некоторые детали.
```

Почему плохо:
- непонятно, какая логика;
- непонятно, где начало и конец процесса;
- нет точки входа.

### Хорошо: описание ветки

```md
### 4.4. Ветка !CanProcess

Если условие не выполняется, новое событие не создается и следующий этап обработки не запускается.

Это значит:
- система завершает flow для этой сущности;
- уже подготовленные изменения просто сохраняются;
- повторный processing chain не стартует без нового события.
```

Почему хорошо:
- есть условие;
- есть результат;
- есть объяснение, что происходит дальше.

### Плохо: описание ветки

```md
### 4.4. Проверка

Тут происходит проверка и иногда ничего не делается.
```

Почему плохо:
- неясно, какая именно проверка;
- неясно, что значит "ничего не делается";
- неясно, как это влияет на дальнейший путь.

## Алгоритм написания README

### Шаг 1. Определи границы документа

Сначала зафиксируй:
- какая точка входа у процесса;
- где заканчивается маршрут, который нужно документировать;
- какая аудитория будет читать README;
- нужен ли акцент на бизнес-смысле, на state mutation, на orchestration или на всем сразу.

### Шаг 2. Пройди реальный кодовый путь

Нужно найти:
- основной entrypoint;
- верхнеуровневые ветки;
- batch/scope/context стадию, если она есть;
- подготовку одной сущности;
- ключевые commands/queries/services;
- финальное действие системы.

### Шаг 3. Выдели крупные этапы

Собери flow в 5-8 основных секций.

Каждая секция должна отражать крупный этап, а не случайный helper.

### Шаг 4. Для каждого этапа опиши смысл и последствия

Проверь, что в каждой секции есть:
- что происходит;
- зачем это нужно;
- что используется;
- что меняется;
- куда flow идет дальше.

### Шаг 5. Добавь ветки, skip-path и safe-path

После базового скелета отдельно добавь все ветки, которые реально меняют дальнейшее поведение.

### Шаг 6. Напиши краткую итоговую схему

После подробного описания добавь короткую секцию, где весь flow повторяется в сжатом виде.

### Шаг 7. Добавь карту файлов

В конце перечисли файлы, которые действительно нужны для навигации по описанному процессу.

### Шаг 8. Проверь документ на читаемость

Перед завершением проверь:
- документ читается сверху вниз без раскрывашек;
- секции не дублируют друг друга;
- важные ветки не потеряны;
- текст не превратился в dump методов;
- после чтения понятен весь процесс.

## Проверка перед завершением

1. В начале README явно названа главная точка входа.
2. Порядок секций соответствует реальному порядку вызовов в коде.
3. Верхнеуровневые ветки описаны отдельно.
4. Для каждого крупного шага понятно, что он делает и зачем он нужен.
5. Подготовка данных, принятие решения и фактическая обработка разделены явно.
6. Важные skip/no-op/save-only/create-event/use-existing branches не потеряны.
7. Ясно отмечено, где логика работает только в памяти, а где начинается реальный side effect.
8. Документация написана простыми словами и не зависит от чтения исходников построчно.
9. В README нет лишних code blocks, если пользователь их отдельно не просил.
10. По умолчанию не используется HTML `details/summary`.
11. В конце есть короткая логика принятия решения.
12. В конце есть карта файлов с ролями.
13. Документ можно читать сверху вниз как один линейный маршрут.
